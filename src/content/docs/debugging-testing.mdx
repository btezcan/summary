## Summary

- **C#** finds many mistakes **before** the program runs (compiler errors with a
  code like `CS0103`, a file and a line). **Python** finds most of them only
  **when the line runs** — unless you use a type checker such as mypy.
- Debug systematically: **reproduce → isolate → form a hypothesis → check it →
  fix → add a test** so the bug can't come back.
- A **debugger** lets you pause at a **breakpoint**, step line by line and watch
  variables. Print statements are the quick alternative.
- **Unit tests** check small pieces of code automatically: **xUnit** (`[Fact]`,
  `[Theory]`, `Assert.Equal`) in C#, **pytest** (functions named `test_…`,
  plain `assert`) in Python.
- Test the **boundaries** — 0, 1, the largest value, the exact limit (`90` and
  `89`). That's where bugs live.

Python's most common errors, and where you'll see them: `SyntaxError` and
`IndentationError` (before anything runs), `NameError` (a typo), `TypeError`
(wrong type, e.g. `"a" + 1`), `AttributeError` (often a `None`), `ValueError`
(e.g. `int("abc")`), `IndexError` and `KeyError`. Chapter 12 shows how to read
their tracebacks.

### A debugging strategy

1. **Reproduce** the bug with the smallest input that shows it.
2. **Isolate** it: which function, which line? Comment out, split, or test
   pieces.
3. **Hypothesize**: "the loop skips the first element".
4. **Check** the hypothesis with a print statement, a debugger or a test — don't
   change code at random.
5. **Fix** the cause, not the symptom.
6. **Add a test** that failed before the fix and passes after it.

<Pair id="debugging-testing/debug-prints">
  The average of 70, 80 and 90 should be 80. The debug output shows the loop
  starting at `i=1`: the first score is never added. A few well-placed prints
  confirm or reject a hypothesis quickly; remove them once the bug is fixed.
</Pair>

### The debugger

Every IDE (VS Code, Visual Studio, Rider, PyCharm) has a debugger with the same
core ideas:

- **Breakpoint** — the program pauses before executing this line.
- **Step over** — run the current line, stop at the next one.
- **Step into** — go inside the method or function called on this line.
- **Watch / Locals** — see variable values while paused.
- **Call stack** — which functions called which to get here (the same
  information as a stack trace or traceback).

Python also has a built-in way to stop: put `breakpoint()` on a line to start the
`pdb` debugger in the terminal there.

### Unit tests

A **unit test** calls a small piece of code with known input and checks the
result automatically. Tests follow the **Arrange–Act–Assert** pattern: prepare the
data, call the code, check the result.

- **C#:** tests live in a separate **test project** (`dotnet new xunit`).
  `[Fact]` marks a test; `[Theory]` with `[InlineData]` runs one test for many
  inputs. Run them with `dotnet test`.
- **Python:** pytest finds files named `test_*.py` and functions named
  `test_…`, and a plain `assert` does the checking. `@pytest.mark.parametrize` is
  the counterpart of `[Theory]`. Run them with `python -m pytest`.

## Common Mistakes

<Mistake lang="cs" title="Assert.True for comparisons" wrong="debugging-testing/m-assert-true" right="debugging-testing/m-assert-true-fixed" wrongFile="GraderTests.cs" rightFile="GraderTests.cs">
  Both tests catch the bug (the grader still has the `> 90` bug), but
  `Assert.True` only reports "Expected True, Actual False". `Assert.Equal` shows
  what came out. The argument order is `Assert.Equal(expected, actual)`.
</Mistake>

<Mistake lang="py" title="A test function without the test_ prefix" wrong="debugging-testing/m-not-collected" right="debugging-testing/m-not-collected-fixed" wrongFile="test_average.py" rightFile="test_average.py">
  pytest only runs functions whose names start with `test`. The wrong version
  contains a failing check, but it never runs — "no tests ran" is not a success.
</Mistake>

<Mistake lang="py" title="Comparing floats with ==" wrong="debugging-testing/m-float-equal" right="debugging-testing/m-float-equal-fixed" wrongFile="test_prices.py" rightFile="test_prices.py">
  `0.1 + 0.2` is `0.30000000000000004` (chapter 2). `pytest.approx` compares
  with a small tolerance. In xUnit, `Assert.Equal(0.3, actual, 10)` compares to
  10 decimal places.
</Mistake>

## Predict the Output

<Predict id="debugging-testing/p-first-error">
  The C# compiler reports **every** error it finds in one build, so you see
  both lines at once. Python stops at the **first** runtime error; the undefined
  name on line 2 is never reached — only mypy reports it without running.
</Predict>

<Predict id="debugging-testing/p-assert-message" lang="py">
  `assert condition, message` raises `AssertionError` with the message when the
  condition is false. Use asserts for "this can't happen" checks and in tests —
  not to validate user input, because `python -O` removes them.
</Predict>

## Working with AI

Good prompts for learning this topic:

- "Here is my function. List the boundary cases a good test suite should cover,
  but don't write the tests — I'll write them and you review them."
- "I have this bug: [expected vs actual]. Ask me questions, one at a time, that
  help me find the cause myself."

<Note type="warning" title="Verify it yourself">
  AI can generate tests quickly, but it often tests only the easy middle values,
  or copies the (buggy) output of the code into the expected values — then the
  tests "pass" and prove nothing. Check each expected value yourself, and make
  sure at least one test **fails** when you deliberately break the code.
</Note>
