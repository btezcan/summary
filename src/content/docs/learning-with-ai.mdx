## Summary

- AI assistants write **plausible** code quickly — and it is sometimes wrong in
  subtle ways. Your value is **understanding, judging and verifying** code, not
  typing it.
- Use AI as a **tutor** ("explain", "ask me questions", "review without fixing"),
  not as a replacement for doing the exercise.
- **Verify everything:** does it compile and run, can you explain every line, what
  happens with empty, `null` / `None`, negative and huge input, are there tests,
  do the APIs really exist, is it idiomatic?
- Translating between C# and Python is where AI makes the most **silent**
  mistakes: integer division, `%`, `??` versus `or`, copying versus sharing.
- Follow your course's rules on AI, and say when you used it.

## Concept

### An honest picture

An AI assistant predicts code that *looks* right for your question. Most of the
time it is. But it has no reliable sense of whether it actually is: it can invent
methods that don't exist, mix up language versions, use Python 2 or .NET
Framework patterns, and miss edge cases — all in confident, well-formatted code.
Everything this site verified by running (chapters 1–17) is exactly the kind of
detail it gets wrong.

That changes what programming skill means. Producing code is cheap now.
**Reading** code, **predicting** what it does, **finding** the case where it
breaks and **explaining** why — that is the skill employers and exams look for,
and it's the one you build by doing the work yourself.

### When not to use AI

- **While you are first learning a concept.** If the AI writes your first loop,
  you don't learn loops. Struggle first; ask afterwards.
- **In labs and exams where it is not allowed.**
- **When you can't yet explain the code it would give you.** If you can't
  explain it, you can't check it — and you can't defend it in an oral exam.

### Prompts that make you learn

Ask for **explanations, questions and reviews**, not finished solutions:

- "Explain this error message, but don't write the fix: …"
- "Explain this code line by line, then ask me three questions that check whether
  I understood it."
- "Review my code. List the problems, but don't give me corrected code."
- "Give me five predict-the-output exercises on [topic], one at a time. Wait for
  my answer before showing the solution."
- "Translate this C# to **idiomatic** Python and list every place where the
  behavior could differ." — then **check each claim by running both versions**.

### A verification checklist

Before you trust AI-generated code — or hand it in:

1. **Does it compile and run?** Build it, run it, read every warning. For Python,
   run mypy too.
2. **Can I explain every line?** If not, ask about that line, or rewrite it.
3. **What about the edge cases?** Empty input, `null` / `None`, zero, negative
   numbers, very large values, Turkish letters, a Turkish-locale computer.
4. **Are there tests?** Write a few, including boundaries. Make sure a test fails
   when you break the code on purpose.
5. **Do the APIs exist?** Look up unfamiliar methods in the official
   documentation, or try them in a two-line program.
6. **Is it modern and idiomatic?** No `ArrayList` or `csc.exe`, no Python 2, no
   "C# written in Python".

### Academic integrity

Your course's rules decide what is allowed. When AI helped you, say so in the way
your instructor asks — in a comment, a report section or a conversation. Never
hand in code you can't explain: understanding it is the assignment.

## Common Mistakes

<Mistake lang="py" title="C# written in Python" wrong="learning-with-ai/m-literal-translation" right="learning-with-ai/m-literal-translation-fixed">
  Both print the same thing, but the first version is a line-by-line translation
  of a C# `for` loop: a manual counter, `str(i) + …`, `i = i + 1`. Idiomatic
  Python uses `enumerate` and an f-string. AI translations often look like the
  first version — ask for idiomatic code, and learn to recognize the difference.
</Mistake>

<Note type="warning" title="The silent translation bugs">
  When code moves between C# and Python, check these first — each one is shown
  with real output in an earlier chapter: `/` on integers (chapter 3), `%` and
  `//` on negative numbers (3), `??` versus `or` (3, 11), integer overflow (2),
  culture-dependent `ToUpper` and `Parse` (4), `range` end (5), mutable default
  arguments (6), struct copies versus shared objects (9), dictionary order (7),
  and tasks that start immediately versus coroutines that don't (16).
</Note>

  **Bug 1:** the loop starts at `i = 1`, so the first score (70) is ignored.
  **Bug 2:** `sum / count` divides two `int`s, so `175 / 2` is `87`, not `87.5`.
  **Bug 3:** there's no `null` check; the compiler even warned about it (CS8602).
  The correct average of the passing scores 70, 90 and 85 is 81.67.

<Predict id="learning-with-ai/bug-hunt" lang="py" question="These Python helpers have three bugs. What does the program print, and where are the bugs?">

  still contains `70`. **Bug 2:** `range(1, …)` skips the first score, so the

## Working with AI

Practice what this chapter describes on something you've already written:

- Take a solution of yours from an earlier chapter and ask: "Review this code for
  bugs, edge cases and style. List the problems, but don't rewrite it." Fix what
  you agree with — and write down one point where you think the AI was wrong,
  and why.

<Note type="warning" title="Verify it yourself">
  Everything on this site was checked by compiling and running it. Hold AI
  answers to the same standard: if you can't run it or find it in the official
  documentation, treat it as a guess.
</Note>
